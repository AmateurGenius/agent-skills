# Unified Delegation Architecture

> **Model (2026-09):** Two-track model with separate wallets for separate jobs.
> Creation attribution carries no semantic weight — position ownership is what
> matters, governed by `deposit`/`redeem` and the `approve()` model.

## Core Principle

**Creation attribution doesn't carry semantic weight — position ownership does.**

The protocol design is intentional:
- `createAtoms`/`createTriples` have NO `receiver` parameter — attribution follows `msg.sender` by design
- `deposit`/`redempt` HAVE a `receiver` parameter — shares mint to `receiver`
- The OWS creates directly; the Smart Wallet deposits with `receiver = Main Account`

This is not a gap to work around. It is the protocol working as designed.

## Two Authority Tracks

### Creation Authority Track

**Purpose:** `createAtoms`, `createTriples` (one-time setup operations)

**Wallet:** OWS (Open Wallet Standard) — a temporary wallet with its own keypair

```
OWS creates directly on its own authority.
No delegation chain. No Main Account involvement.
```

**Characteristics:**
- OWS is a temporary wallet generated by the Agent
- The Agent holds the OWS keypair as its primary key
- `msg.sender` at MultiVault = OWS (acceptable — creation attribution is intentional)
- No `approve` needed on MultiVault
- No delegation chain needed — OWS acts directly
- After creation is complete, the OWS key can be discarded or retained for future creation

**Setup flow:**
1. Agent generates OWS keypair: `cast wallet new`
2. Fund OWS with tTRUST for creation costs + gas
3. Optional: Upgrade OWS to EIP-7702 for future delegation support
4. OWS creates atoms/triples directly via Path B (standard write operations)

**Agent execution:**
```
OWS (Path B direct call):
  createAtoms(atomData, assets)
Result: msg.sender = OWS, atom created, attribution = OWS (intentional by design)
```

### Deposit/Redemption Authority Track

**Purpose:** `deposit`, `redeem`, batch variants (standing operations)

**Wallet:** Hybrid Smart Account — a Main Account-derived contract

```
Main Account --(approve)--> Smart Wallet (on MultiVault)
Smart Wallet --(EIP-712 delegation)--> Agent
```

**Characteristics:**
- Smart Wallet is a Main Account-derived contract (CREATE2 or EIP-7702)
- Main Account is the contract owner — no private key exists for the Smart Wallet
- `msg.sender` at MultiVault = Smart Wallet
- `receiver = Main Account` routes shares correctly
- Revocable: revoke Smart Wallet delegation or remove `approve`

**Setup flow:**
1. Main Account calls `approve(SmartWallet, 3)` on MultiVault (signed in MetaMask)
2. Smart Wallet signs EIP-712 delegation to Agent (Main Account signs as contract owner)
3. Agent stores the signed delegation for future use

**Agent execution:**
```
Agent calls:
  redeemDelegations(
    [Smart Wallet → Agent],
    deposit(receiver: Main Account, ...)
  )
Result: msg.sender = Smart Wallet, receiver = Main Account, shares minted to Main Account
```

## Composition (Full Agent)

For a complete agent that both creates and deposits:

```
Phase 1 — Setup:
  Creation: Agent generates OWS keypair, funds it with tTRUST
  Deposit:  Main Account approves Smart Wallet on MultiVault
            Smart Wallet delegates to Agent

Phase 2 — Operations (Agent autonomous):
  Creation:  OWS creates atoms/triples directly (Path B)
  Deposit:   Agent calls redeemDelegations([SmartWallet→Agent], deposit(receiver: MainAcc, ...))

Phase 3 — Management (optional):
  Creation: OWS key can be discarded after creation complete
  Deposit:  Revoke Smart Wallet delegation (kill switch)
```

## Key Separation (3 roles)

| Role | Owner | Persisted? |
|------|-------|------------|
| Main Account key | User | Never |
| Agent key (= OWS key) | Agent | Yes (`~/.intuition/agent-wallet.json`) |

> **Clarification:** The Agent has ONE key: the OWS key. The OWS is a
> temporary wallet with its own keypair — the Agent generates it and uses
> it as its primary key for broadcasting and for the creation track.
> The Smart Wallet is a Main Account-derived contract (CREATE2 or EIP-7702)
> with NO private key. The Main Account is its contract owner.

## Comparison with Old Model

| Concept | Old (Two-hop chain for creation) | New (Direct creation + delegated deposit) |
|---|---|---|
| Architecture | Complex two-hop chain for all operations | Simple: OWS creates directly, Smart Wallet deposits |
| Creation attribution | Tried to route through Main Account | OWS (acceptable — no semantic weight) |
| Main Account involvement | Required for every creation | None for creation; one-time approve for deposit |
| Deposit attribution | Via delegation chain | Via `receiver = Main Account` |
| Approve needed? | Complex chain for creation | Deposit track only |
| Revocation | Multi-hop revocation | OWS: discard key; Deposit: revoke delegation |
