# Creation Authority Track

Documents the OWS (Open Wallet Standard) track for `createAtoms` and `createTriples`.

## Architecture

```
OWS creates atoms/triples directly on its own authority.
No delegation chain. No Main Account involvement.
```

The OWS is a temporary wallet generated by the Agent. It exists only during
the creation window. After creation operations are complete, its key can be
discarded or retained for future creation.

## Why a separate wallet?

`createAtoms` and `createTriples` have no `receiver` parameter by design.
Attribution follows `msg.sender`. This is intentional — creation attribution
carries no semantic weight in the Intuition protocol.

The OWS solves a simple problem: it gives the Agent a dedicated wallet for
creation operations, separate from the Main Account. This means:
- The Main Account private key is never needed for creation
- The OWS key can be discarded after creation is complete
- Position ownership is established separately via the deposit track

## Setup (one-time)

### Step 1: Create OWS

Generate a temporary keypair. This is the OWS (Open Wallet Standard).

```bash
# Generate OWS keypair (cast wallet)
OWS_KEYS=$(cast wallet new)
OWS_ADDRESS=$(echo "$OWS_KEYS" | grep "Address" | awk '{print $2}')
OWS_PK=$(echo "$OWS_KEYS" | grep "Private Key" | awk '{print $3}')
```

Save the keypair to `~/.intuition/agent-wallet.json` (chmod 600). This IS
the Agent's primary key.

### Step 2: Fund OWS

The OWS needs tTRUST for:
- Creation costs (~1 tTRUST per atom/triple)
- Gas for transactions

```bash
# Fund OWS from Main Account or any funded wallet
cast send $OWS_ADDRESS --value 2ether --private-key $FUNDING_PK --rpc-url $RPC
```

### Step 3: Optional — Upgrade OWS to EIP-7702

For future delegation support, upgrade the OWS to EIP-7702:

```bash
cast send $OWS_ADDRESS \
  --auth $EIP7702_IMPLEMENTATION \
  --private-key $OWS_PK \
  --rpc-url $RPC

# Verify
cast code $OWS_ADDRESS --rpc-url $RPC
# Should start with: 0xef0100<implementation-address>
```

> **Pitfall:** `--auth` expects the implementation address directly, NOT `0xef0100...`.

## Agent Execution

The OWS creates atoms/triples directly via Path B (standard write operations).
No delegation chain, no `redeemDelegations` wrapper.

```bash
# OWS creates atom directly
cast send $MULTIVAULT "createAtoms(bytes[],uint256[])" "[$ATOM_DATA]" "[$ATOM_COST]" \
  --private-key $OWS_PK \
  --value $ATOM_COST \
  --rpc-url $RPC
```

Result: `msg.sender` = OWS, atom created, attribution = OWS (intentional by design).

## Attribution

- `msg.sender` at MultiVault = OWS
- No `receiver` parameter for creation
- Atom/triple attribution follows `msg.sender` = OWS
- This is acceptable: creation attribution is cosmetic, position ownership is semantic
- Position ownership is established via deposit track (`receiver = Main Account`)

## Cleanup

After all atoms/triples are created:
- The OWS key can be discarded (no on-chain revocation needed)
- Or retained for future creation operations
